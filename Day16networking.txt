================================================================================
                      LINUX SYSTEM ADMINISTRATION NOTES
                 MODULE: NETWORK PATH DIAGNOSTICS (traceroute)
================================================================================

1. INTRODUCTION
--------------------------------------------------------------------------------
Command      : traceroute
Binary Path  : /usr/bin/traceroute
Package      : traceroute
Protocols    : UDP (Default in Linux), ICMP (-I flag), TCP (-T flag)
Description  : A network diagnostic tool used to track the path (hops) that data 
               packets take from source to destination, measuring round-trip latency 
               at each intermediate router.
Windows Alt  : `tracert`


2. REAL-WORLD USES
--------------------------------------------------------------------------------
1. ISP / Routing Bottlenecks : Identify which specific router or ISP in the path 
                               is causing high latency or packet loss.
2. Firewall / Drop Detection : Isolate where packets are being silently dropped (* * *).
3. Network Path Optimization : Verify if traffic is taking the expected geographic 
                               or BGP routing route.
4. Port / Service Probing    : Test TCP connection paths to web/database ports (-T -p).


3. KEY FLAGS & COMMAND VARIATIONS
--------------------------------------------------------------------------------
Task                                    Command
--------------------------------------------------------------------------------
Traceroute domain (Default UDP)         : traceroute google.com
Disable DNS resolution (Fast, show IPs) : traceroute -n 8.8.8.8
Use ICMP Echo packets (Like Windows)    : sudo traceroute -I google.com
Use TCP SYN packets (Bypass firewalls)  : sudo traceroute -T -p 443 google.com
Set max hops limit (Default: 30)        : traceroute -m 15 google.com
Set queries per hop (Default: 3 probes) : traceroute -q 1 google.com
Set probe response timeout (e.g., 2s)   : traceroute -w 2 google.com
Specify outbound interface              : traceroute -i ens33 8.8.8.8


4. SAMPLE OUTPUT BREAKDOWN
--------------------------------------------------------------------------------
Command: traceroute -n -m 5 google.com

Sample Output:
traceroute to google.com (142.250.190.46), 30 hops max, 60 byte packets
 1  192.168.1.1  1.124 ms  1.089 ms  0.985 ms
 2  10.240.0.1  8.452 ms  8.112 ms  8.341 ms
 3  172.16.100.5  12.891 ms  11.450 ms  12.110 ms
 4  * * *
 5  142.250.190.46  14.210 ms  13.980 ms  14.050 ms

Metrics Explained:
- Column 1 (1, 2, 3...) : Hop number (Sequential count of routers).
- Column 2 (IP Address) : IP address of the router handling that hop.
- Columns 3, 4, 5 (ms)  : Round-trip time (RTT) for 3 separate probe packets sent to that hop.
- Line 4 (* * *)        : Router/Firewall at Hop 4 blocked UDP/ICMP probes (Timed out), 
                          or ICMP rate-limiting was triggered.


5. REAL-WORLD TROUBLESHOOTING SCENARIO
--------------------------------------------------------------------------------
Scenario: Website `example.com` is unreachable. `ping` fails completely.

Troubleshooting Steps:
1. Run Standard Traceroute       : `traceroute example.com`
                                   (Output hangs with `* * *` starting from Hop 3).
2. Skip DNS Lookup for Speed     : `traceroute -n example.com`
                                   (Confirms Hop 3 IP is `49.207.0.1` - ISP Gateway).
3. Bypass UDP Block via ICMP     : `sudo traceroute -I example.com`
                                   (If still blocked, UDP/ICMP is filtered at Hop 3).
4. Probe via TCP Port 80/443     : `sudo traceroute -T -p 443 example.com`
                                   (Traffic passes through! Proves web port is open, 
                                    but standard ping/UDP is blocked by corporate firewall).


6. REVISION CHEATSHEET
--------------------------------------------------------------------------------
- `* * *` does NOT always mean the server is down; routers often drop ICMP/UDP probes for security.
- Always use `-n` in production troubleshooting to avoid slow DNS reverse-lookups.
- Use `-T -p <port>` when troubleshooting specific web or database services behind strict firewalls.

================================================================================
                      LINUX SYSTEM ADMINISTRATION NOTES
                 MODULE: PORT REACHABILITY & NETWORK DIAGNOSTICS (telnet)
================================================================================

1. INTRODUCTION
--------------------------------------------------------------------------------
Command      : telnet (Teletype Network Protocol)
Binary Path  : /usr/bin/telnet
Package      : telnet
Protocol     : TCP (Layer 4 / Transport Layer)
Description  : A client-server protocol used to test TCP port connectivity and 
               interact with text-based network services.
Security Note: UNENCRYPTED protocol. Passwords and data are transmitted in plain text.
Modern Alt   : `nc` (Netcat) or `nmap` for port scanning; `ssh` for remote administration.


2. REAL-WORLD USES
--------------------------------------------------------------------------------
1. Firewall / Port Probing  : Test if a remote host's TCP port (e.g., 80, 443, 3306, 5432) 
                              is open and reachable through firewalls.
2. Application Health Check  : Verify if web servers, mail servers (SMTP), or database 
                              daemons are accepting connections.
3. Service Banner Grabbing   : Inspect daemon versions exposed on open ports.
4. HTTP/SMTP Debugging       : Manually craft RAW HTTP requests or test SMTP mail flow.


3. KEY COMMAND VARIATIONS & INTERACTIVE KEYS
--------------------------------------------------------------------------------
Task                                    Command
--------------------------------------------------------------------------------
Test TCP port connection               : telnet google.com 80
Test custom service port (e.g., MySQL) : telnet 192.168.1.100 3306
Test SSH port connectivity              : telnet 192.168.1.100 22
Escape/Exit interactive Telnet session : Press `Ctrl + ]`, then type `quit` and press Enter.


4. SAMPLE OUTPUT BREAKDOWN
--------------------------------------------------------------------------------
Scenario A: SUCCESSFUL CONNECTION (Port is Open & Reachable)
$ telnet google.com 80

Output:
Trying 142.250.190.46...
Connected to google.com.
Escape character is '^]'.

Explanation:
- `Connected to google.com`: TCP 3-way handshake succeeded. The port is open and 
  firewall is NOT blocking connection.


Scenario B: CONNECTION REFUSED (Port is Closed / Service Down)
$ telnet 192.168.1.100 3306

Output:
Trying 192.168.1.100...
telnet: Unable to connect to remote host: Connection refused

Explanation:
- `Connection refused`: The remote machine is reachable, but NO process is listening 
  on port 3306 (or local firewall reset the connection).


Scenario C: CONNECTION TIMED OUT (Firewall Blocking)
$ telnet 192.168.1.100 3306

Output:
Trying 192.168.1.100...
telnet: Unable to connect to remote host: Connection timed out

Explanation:
- `Connection timed out`: Network packets are being silently dropped. Indicates a 
  FIREWALL (AWS Security Group, iptables, ufw) is blocking the port.


5. REAL-WORLD TROUBLESHOOTING SCENARIO
--------------------------------------------------------------------------------
Scenario: Web application running on Web Server A cannot connect to PostgreSQL 
          Database Server B (192.168.1.50) on Port 5432.

Troubleshooting Steps:
1. Test Physical Network     : Run `ping 192.168.1.50` (Ensure host is reachable).
2. Test TCP Port Reachability: Run `telnet 192.168.1.50 5432`.
3. Analyze Outcome           :
   - If `Connected`: Connection works! Check app database credentials/config.
   - If `Connection refused`: DB service is stopped or postgresql.conf isn't listening on 0.0.0.0.
   - If `Connection timed out`: Firewall issue! Update UFW/iptables or AWS Security Group rules.


6. REVISION CHEATSHEET
--------------------------------------------------------------------------------
- Syntax Pattern: `telnet <HOST/IP> <PORT_NUMBER>`
- Never use `telnet` for remote shell logins over public networks (use `ssh`).
- To force quit an active/stuck telnet session: Press `Ctrl + ]`, then type `q` and hit Enter.
- `telnet` tests ONLY TCP ports. It CANNOT test UDP ports (use `nc -zu` for UDP).

================================================================================
                      LINUX SYSTEM ADMINISTRATION NOTES
                 MODULE: NETWORKING SWISS ARMY KNIFE (nc - Netcat)
================================================================================

1. INTRODUCTION
--------------------------------------------------------------------------------
Command      : nc (Netcat / ncat)
Binary Path  : /usr/bin/nc or /bin/nc
Package      : netcat-openbsd / netcat-traditional / ncat
Protocols    : TCP & UDP (Layer 4 / Transport Layer)
Description  : A feature-rich networking utility used to read from and write to 
               network connections using TCP or UDP protocols.
Nickname     : "The Swiss Army Knife of Networking".


2. REAL-WORLD USES
--------------------------------------------------------------------------------
1. TCP Port Scanning        : Check if single or multiple TCP ports are open/listening.
2. UDP Port Testing         : Test UDP port reachability (which `telnet` cannot do).
3. Direct File Transfer     : Transfer raw files directly between two Linux systems.
4. Port Listening / Web Server: Create quick temporary TCP/UDP listeners for testing.
5. Service Banner Grabbing   : Inspect daemon versions running on specific ports.


3. KEY FLAGS & COMMAND VARIATIONS
--------------------------------------------------------------------------------
Flag    Purpose / Meaning               Example Command
--------------------------------------------------------------------------------
-z      Zero-I/O Mode (Scanning mode)  : nc -zv 192.168.1.100 80
-v      Verbose (Detailed output)       : nc -v google.com 443
-u      UDP Mode (Default is TCP)       : nc -uzv 192.168.1.100 53
-l      Listen Mode (Start a listener)  : nc -l -p 8080
-p      Specify Port Number            : nc -l -p 9000
-w      Set Timeout (e.g., 3 seconds)  : nc -zv -w 3 192.168.1.100 22-80
-n      Skip DNS Lookup (Numeric IPs)   : nc -zv -n 192.168.1.100 3306


4. PRACTICAL COMMAND EXAMPLES
--------------------------------------------------------------------------------
1. Scan Single TCP Port:
   $ nc -zv 192.168.1.100 22

2. Scan Range of Ports (e.g., 20 to 80):
   $ nc -zv -w 2 192.168.1.100 20-80

3. Test UDP Port (DNS Port 53):
   $ nc -uzv 192.168.1.100 53

4. Transfer a File between Two Servers:
   - On Receiver Server B (IP: 192.168.1.50):
     $ nc -l -p 9000 > received_file.txt
   - On Sender Server A:
     $ nc 192.168.1.50 9000 < sample_file.txt

5. Create a Simple Terminal Chat / Data Pipeline:
   - On Server A: `nc -l -p 1234`
   - On Server B: `nc 192.168.1.ServerA_IP 1234`


5. SAMPLE OUTPUT BREAKDOWN
--------------------------------------------------------------------------------
Scenario A: SUCCESSFUL TCP PORT SCAN
$ nc -zv 192.168.1.100 22

Output:
Connection to 192.168.1.100 22 port [tcp/ssh] succeeded!

Explanation:
- Target IP is reachable and TCP port 22 is open and actively listening.


Scenario B: CLOSED PORT / REFUSED
$ nc -zv 192.168.1.100 3306

Output:
nc: connect to 192.168.1.100 port 3306 (tcp) failed: Connection refused

Explanation:
- Host is reachable, but no service is listening on port 3306.


6. REAL-WORLD TROUBLESHOOTING SCENARIO
--------------------------------------------------------------------------------
Scenario: Application fails to send logs to syslog server over UDP port 514. 
          Need to confirm if UDP port 514 is open through corporate firewall.

Troubleshooting Steps:
1. Run Netcat in UDP Scan Mode : `nc -uzv -w 3 192.168.1.50 514`
2. If Output shows `succeeded`  : Network/Firewall is open. Issue is in Syslog config.
3. If Output times out         : Firewall (UFW/AWS Security Group) is blocking UDP 514.


7. REVISION CHEATSHEET
--------------------------------------------------------------------------------
- Always use `-z` for scanning (prevents Netcat from hanging waiting for input).
- Use `-u` flag whenever testing UDP services (DNS, NTP, Syslog, SNMP).
- Netcat is unencrypted by default; do not send sensitive data over untrusted networks.
- Modern `ncat` (Nmap suite) supports SSL/TLS encryption using `--ssl` flag.

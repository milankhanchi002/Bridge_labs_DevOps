CURL -V / CURL -VERBOSE OUTPUT — COMPLETE NETWORKING EXPLANATION
===============================================================

Command used:
    curl -v https://google.com

What does -v mean?
------------------
-v means verbose mode.

Normally curl only shows the response body.

With -v, curl shows the complete communication process, including:

DNS resolution
IPv6 / IPv4 selection
TCP connection
TLS handshake
Certificate verification
ALPN negotiation
HTTP/2 communication
HTTP request
HTTP response
Redirect
Connection status

===============================================================
2. DNS RESOLUTION
===============================================================

Output:

    * Host google.com:443 was resolved.
    * IPv6: 2404:6800:4002:81b::200e
    * IPv4: 142.250.182.206


Meaning:

google.com is a domain name.

Computers communicate using IP addresses, so the domain name must first
be translated into an IP address.

DNS = Domain Name System

DNS performs:

    Domain Name
         |
         v
    IP Address

Example:

    google.com
         |
         v
    142.250.182.206


Google returned both:

IPv6:

    2404:6800:4002:81b::200e

IPv4:

    142.250.182.206


Why are there two?

Because the Internet supports:

    IPv4
    IPv6


Conceptually:

    curl
      |
      | DNS Query
      v
    DNS Resolver
      |
      +---- IPv6 address
      |
      +---- IPv4 address


Important:

DNS does NOT establish the connection.

DNS only helps us find the IP address of the destination.


===============================================================
3. IPv6 ATTEMPT
===============================================================

Output:

    * Trying [2404:6800:4002:81b::200e]:443...


Curl is trying to connect to:

    IPv6 address
        +
    TCP port 443


Port 443 normally means HTTPS.


Then:

    * Immediate connect fail for
      2404:6800:4002:81b::200e:
      Network is unreachable


Meaning:

The machine knows the IPv6 address, but it does not have a usable
network route to reach that IPv6 destination.


This does NOT mean:

    Google is down.

It means:

    Your machine/network does not currently have a working IPv6 path.


Conceptually:

    Your Machine
         |
         | IPv6 packet
         X
      No IPv6 route
         |
         X
      Destination


Useful Linux commands:

    ip -6 addr

Shows IPv6 addresses configured on interfaces.

    ip -6 route

Shows IPv6 routing table.


===============================================================
4. IPv4 FALLBACK
===============================================================

After IPv6 fails, curl tries IPv4:

    * Trying 142.250.182.206:443...


Now curl tries:

    Destination IP = 142.250.182.206
    Destination Port = 443


This succeeds.


Conceptually:

    Your Machine
    192.168.64.5
          |
          | IPv4
          |
          v
    142.250.182.206
       Google


This is an example of IPv4 fallback when IPv6 connectivity is not available.

The output later says:

    * Established connection to google.com

      from 192.168.64.5 port 52184


This tells us:

    192.168.64.5:52184
            |

            |

Important concept:

The client usually gets a temporary/ephemeral port.

The server listens on a well-known service port.

Here:

    Client port = 52184
    Server port = 443


===============================================================
6. TCP THREE-WAY HANDSHAKE
===============================================================

Before TLS starts, TCP must establish a connection.

TCP uses the three-way handshake:

    Client                         Server
      |                              |
      | -------- SYN --------------> |
      | <------- SYN-ACK ----------- |
      | -------- ACK --------------> |
      |                              |
      |       TCP established        |


The three steps are:

    1. SYN
    2. SYN-ACK
    3. ACK


Important:

TLS does NOT happen before TCP when HTTPS is running over TCP.

The order is:

    DNS
      |
    TCP
      |
    TLS
      |
    HTTP

    h2 = HTTP/2


Then Google responds:

Conceptually:

       v
    Server
       |
       | Let's use HTTP/2
       v
    HTTP/2

40. HOW TO DEBUG A CURL CONNECTION
===============================================================

If curl fails, think layer-by-layer.


STEP 1 — DNS

Check:

    nslookup google.com

or:

    dig google.com

Question:

    Did the hostname resolve to an IP?


If not:

    DNS problem


STEP 2 — ROUTING

Check:

    ip route

For IPv6:

    ip -6 route


Question:

    Does the machine have a route to the destination?


STEP 3 — CONNECTIVITY

Test:

    ping google.com

For IPv4:

    ping -4 google.com

For IPv6:

    ping -6 google.com


Note:

Ping uses ICMP, not TCP 443, so ping failure does not always
mean HTTPS will fail.


STEP 4 — TCP PORT

Test:

    nc -vz google.com 443


or:

    telnet google.com 443


Question:

    Can I establish a TCP connection to port 443?


STEP 5 — TLS

Use:

    curl -v https://google.com


or:

    openssl s_client -connect google.com:443 -servername google.com


Question:

    Is the TLS handshake succeeding?


STEP 6 — HTTP

Use:

    curl -v https://google.com


Question:

    What HTTP status code did the server return?

===============================================================
42. IMPORTANT INTERVIEW QUESTION
===============================================================

Question:

    What happens when you run:

        curl https://google.com


Answer:

    First, the system resolves google.com using DNS and gets
    IPv4 and/or IPv6 addresses.

    Curl tries IPv6 first in this case, but IPv6 fails because
    there is no reachable IPv6 route.

    Curl then falls back to IPv4 and connects to Google's
    IPv4 address on TCP port 443.

    TCP establishes the connection using the three-way handshake.

    After TCP is established, TLS 1.3 negotiation takes place.

    The server sends its certificate, and the client verifies
    the certificate chain, trusted CA, validity, and hostname.

    After successful TLS negotiation, ALPN negotiates HTTP/2.

    Curl then sends an HTTP GET request for the "/" path.

    Google responds with HTTP 301 and provides
    https://www.google.com/ in the Location header.

    If curl is run with -L, it follows the redirect automatically.


===============================================================
43. SHORT INTERVIEW VERSION
===============================================================

If the interviewer wants a short answer:

    When I run curl https://google.com, DNS first resolves the
    hostname to an IP address. Curl then establishes a TCP
    connection to port 443. After that, TLS performs the secure
    handshake and certificate verification. ALPN negotiates the
    application protocol, which in this case is HTTP/2. Curl
    sends an HTTP GET request, and the server returns an HTTP
    response. In this example Google returns 301 and redirects
    google.com to www.google.com.

47. MOST IMPORTANT DEVOPS LEARNING
===============================================================

Do not memorize curl output line-by-line.

Understand the layers.

When a connection fails, ask:

    1. Did DNS resolve?
           |
           v
    2. Do I have a route?
           |
           v
    3. Can I establish TCP?
           |
           v
    4. Can TLS handshake complete?
           |
           v
    5. Is the certificate trusted?
           |
           v
    6. Does hostname match?
           |
           v
    7. Which HTTP version was negotiated?
           |
           v
    8. What HTTP status code did the server return?


This approach is much more useful in Linux, DevOps,
Cloud, Kubernetes, networking, and production troubleshooting
than simply memorizing commands.
